# 手機 IMU 室內行走軌跡偵測網頁 — 技術規格書

版本：v0.1 draft
目的：讓多名使用者各自用手機走一段路線（含上下樓、轉彎、迴走），網頁即時畫出推算路線並輸出 XYZ 連續座標序列 + 原始感測器數據，供主管做多人 3D 軌跡精準度比較，並可重跑不同定位演算法。

---

## 1. 專案目標與使用情境

1. 使用者點「開始偵測」→ 手持/口袋放置手機 → 走一段路線（可能上下樓、順時針/逆時針繞行、原路折返）→ 走回原點或某定點 → 點「停止」。
2. 網頁即時顯示推算出的 2D/3D 路線圖（即時回饋，非事後才看到）。
3. 停止後，網頁提供「輸出」：
   - **Track（推算座標序列）**：一串 `(x, y, z, t)`，單位公尺／毫秒，Y 軸=北，Z 軸=垂直高度。
   - **Raw Sensor Log（原始感測器數據）**：加速度、角速度、磁力、姿態四元數等原始讀數＋時間戳，供事後重新套用不同定位演算法。
4. 多名使用者各自走（可能走同一條實體路線、或各走各的），主管把每個人輸出的數值貼到比較工具裡，比較「誰的路徑形狀/距離/樓層變化最接近真實路線」。

### 1.1 本專案刻意不做的事（範圍界線）
- 不做絕對座標定位（GPS級、room-level anchor），這是**相對航位推算（PDR, Pedestrian Dead Reckoning）**，起點永遠是 (0,0,0)。
- 不假裝能做到測量級精度。手機 MEMS 感測器 + 單純雙重積分的水平位移誤差會隨時間發散（這是 IMU 定位的物理限制，業界用 PDR+步伐偵測+ZUPT 緩解，但無法消除），規格書會明確標註「已知誤差來源」，讓主管在比較時知道這是本質限制、不是程式bug。
- 不做樓層氣壓計偵測（Web 瀏覽器目前對 Barometer API 支援度幾乎為零，iOS Safari 完全不支援），改用加速度波形+垂直/水平位移比值的方式反推樓梯段。

## 2. 精度影響因子總表（先列出，後面章節逐一對應設計）

| # | 因子 | 影響 | 本設計的對策 |
|---|------|------|-------------|
| 1 | 手機放置位置（手持/褲袋/外套胸袋/背包） | 改變感測器座標系原點與人體的相對關係、晃動幅度、步伐衝量大小 | 要求使用者在開始前選擇「攜帶方式」選項，記錄進 metadata；不同攜帶方式套用不同步伐偵測門檻值（見 §4.2） |
| 2 | 手機姿態（直放/橫放/倒放） | 加速度計原始讀數的座標軸對應不同 | 用姿態四元數做座標轉換，統一轉為世界座標系（見 §4.1），不依賴手機固定方向 |
| 3 | 不同使用者走路步態差異（步幅、步頻、左右腳不對稱） | 影響步長估計，進而影響水平距離誤差 | 開場要求輸入身高（選填）用於初始步長估計；系統採用動態步長模型（Weinberg / Kim 公式），依加速度波峰動態調整步長，而非固定步長 |
| 4 | 步伐偵測誤判（漏判/誤判） | 距離估計誤差直接累積 | 使用峰值檢測＋步頻合理性過濾（0.5–3.5 Hz）＋最小步間時間鎖定（見 §4.2） |
| 5 | 陀螺儀零偏（gyro bias/drift） | 航向角隨時間緩慢漂移，是 PDR 最大誤差源 | 用加速度計+磁力計做姿態融合校正陀螺儀（Madgwick/Mahony filter），非純陀螺儀積分（見 §4.1） |
| 6 | 磁力計受環境鐵磁干擾（電梯、鋼筋、家電） | 航向角瞬間跳動 | 偵測磁場強度異常（與地磁合理範圍 25–65 µT 比較），超出範圍時該時刻降低磁力計權重，改依賴陀螺儀短期積分（見 §4.1） |
| 7 | 走樓梯時的垂直運動與水平運動耦合 | 誤把垂直加速度算進水平位移，或反之 | 先做世界座標轉換分離垂直/水平加速度軸，再各自做步伐週期內的位移積分（見 §4.3） |
| 8 | 手機瀏覽器 API 取樣率不穩定（不同手機/瀏覽器差異，iOS 低功耗時會降頻） | 時間戳不均勻，積分誤差變大 | 不假設固定頻率，每筆數據帶實際 timestamp，演算法用「時間加權積分」而非「次數積分」；記錄實際取樣率供事後評估數據品質（見 §5） |
| 9 | 感測器權限與瀏覽器相容性（iOS 13+ 需使用者手動授權 DeviceMotion） | 沒授權就拿不到數據 | 開場明確的權限請求流程+相容性檢測+失敗提示（見 §6） |
| 10 | 雙重積分的誤差隨時間發散（IMU 本質問題） | 走得越久/越遠，推算位置誤差越大 | 1) 用 ZUPT（Zero velocity update，偵測步伐間的靜止時刻把速度重置為0，而非持續積分）取代純加速度雙重積分；2) 若使用者選擇「回到起點」，記錄閉合誤差（closure error）作為這趟路線整體精度指標，回傳給主管參考（見 §4.4） |
| 11 | 轉彎/迴轉時角速度瞬間變化大 | 容易產生偽步伐或航向角突跳 | 轉彎時角速度超過門檻會暫停步長累積、只更新航向，避免轉身動作被誤判為位移（見 §4.2） |

純前端（Vanilla JS + 一個輕量 3D 繪圖庫），不需要後端伺服器；資料全部留在裝置端，使用者自己複製/下載輸出檔。

### 技術選型
- **語言**：HTML + CSS + 原生 JavaScript（ES6+），避免框架相依性，方便直接用手機瀏覽器開啟（可放靜態檔案伺服器或直接開 file://，但 iOS 權限 API 需 HTTPS，建議部署到任一靜態 hosting 如 GitHub Pages）。
- **3D 可視化**：Three.js（CDN 引入），畫 3D 折線＋目前朝向箭頭；2D 俯視圖用 Canvas 2D 作為輔助視圖（更直覺看「平面走的方不方正」）。
- **感測器 API**：
  - `DeviceMotionEvent`（含 `acceleration`, `accelerationIncludingGravity`, `rotationRate`, `interval`）
  - `DeviceOrientationEvent`（含 `alpha/beta/gamma`，以及 iOS 的 `webkitCompassHeading`）
  - 若裝置支援，優先使用 `Generic Sensor API`（`Accelerometer`, `Gyroscope`, `Magnetometer`）取得更原始、更高頻的數據；偵測不到則 fallback 到上面兩個 Event API。

## 4. 核心演算法設計（PDR, Pedestrian Dead Reckoning）

### 4.1 座標系定義與姿態融合

**世界座標系（本專案統一採用）**：
- X 軸：東
- Y 軸：北
- Z 軸：垂直向上
- 原點：使用者按下「開始偵測」那一刻的位置 (0,0,0)，朝向以當下手機朝向或磁北校正後的方向為基準

**手機座標系→世界座標系轉換步驟**：
1. 讀取 `accelerationIncludingGravity`（含重力分量，用來估計重力方向＝垂直向下方向）與 `rotationRate`（角速度）。
2. 用 **Madgwick 互補濾波演算法**（開源、計算量小、適合瀏覽器 JS 即時運算）融合加速度計+陀螺儀+磁力計，輸出姿態四元數 `q(t)`。
   - 陀螺儀：短時間內準確，但會漂移（零偏隨溫度/時間緩慢偏移）
   - 加速度計：長時間平均方向準確（指向重力），但瞬間晃動時不可靠
   - 磁力計：提供絕對航向參考（指北），但易受金屬/電器干擾
   - 互補濾波用「加速度計+磁力計的長期穩定性」持續修正「陀螺儀積分的漂移」
3. 用姿態四元數把手機座標系的線性加速度（扣除重力後）旋轉到世界座標系：
   `a_world = q * a_device_linear * q⁻¹`
4. 此時 `a_world.z` 是真實垂直加速度，`a_world.x/y` 是真實水平加速度 — 這是後續「樓梯斜度反推」「步伐偵測」都要用這組轉換後的值，而非手機原始讀數。

**磁場異常偵測（因子#6對策）**：
- 計算磁力計三軸向量模長 `|B| = sqrt(mx²+my²+mz²)`
- 地球磁場合理範圍約 25–65 µT；若 `|B|` 超出 [20, 80] µT 持續偵測，將該時間段磁力計權重動態降到接近 0，航向改依賴陀螺儀短期積分 + 記錄「此區段航向可信度降低」旗標，一併輸出給主管參考。

### 4.2 步伐偵測（Step Detection）與動態步長（Step Length Estimation）

**步伐偵測**：
- 對世界座標系垂直加速度 `a_world.z` 做低通濾波（截止頻率約 3Hz，濾除高頻手部晃動雜訊）
- 偵測波峰（peak detection）：波峰需滿足
  - 振幅超過動態門檻（門檻值依「攜帶方式」設定，見下表，因子#1對策）
  - 與前一步峰值的時間間隔在 0.25–2.0 秒之間（對應步頻 0.5–3.5 Hz，因子#4對策，排除手抖/車震等非步伐訊號）

| 攜帶方式 | 加速度峰值門檻（建議初始值，可在使用中自適應微調） | 備註 |
|---------|---------------------------------------|------|
| 手持（看手機走） | 1.2 m/s² | 晃動較大，門檻稍高 |
| 褲子口袋 | 0.8 m/s² | 貼近身體核心，波形最乾淨 |
| 外套/上衣口袋 | 1.0 m/s² | 中等晃動 |
| 手臂臂帶/背包 | 0.9 m/s² | 中等偏穩定 |

> 使用者在「開始偵測」前必須選擇攜帶方式（必填），此為 metadata 的一部分跟著輸出，供主管比較時排除「不同攜帶方式造成的系統性差異」。

**動態步長估計（因子#3對策，取代固定步長假設）**：
採用修改版 Weinberg 公式，依每一步加速度波形的峰谷差動態計算步長，而非固定「每步 70cm」這種不符合現實的假設：

```
step_length = K × (a_max - a_min)^(1/4)
```
- `a_max, a_min`：該步週期內垂直加速度的最大值與最小值
- `K`：個人化係數，初始預設 0.5（身高170cm的統計平均值），若使用者填寫身高，用 `K = height(m) × 0.42` 做初始校正；實際系統仍以加速度動態反推為主，身高只影響初始係數，不是直接拿身高除步數這種不合理的簡化。

**轉彎抑制（因子#11對策）**：
- 當 `|rotationRate.z|`（世界座標系偏航角速度）超過 100°/s 持續 >150ms，判定為「轉身/迴轉動作」，該時間段只更新航向角，不累積步長位移（避免轉身的軀幹擺動被誤判為一步）。

### 4.3 樓梯/斜坡偵測與斜度反推（因子#7對策，核心重點）

**不使用固定角度假設，不使用手機姿態角當斜度**（理由見前述對話：手機姿態角反映的是攜帶方式，不是路線斜度）。改用以下流程：

1. 每偵測到一步，已知該步的「世界座標水平位移分量」（由步長+當前航向角算出 Δx, Δy）與「世界座標垂直位移分量」Δz。
2. **垂直位移 Δz 怎麼來**：對世界座標垂直加速度 `a_world.z` 在該步週期內做二次積分，並在每一步結束瞬間（偵測到速度過零點，即 ZUPT 時機，見 §4.4）校正垂直速度歸零，防止垂直方向誤差無限累積。
3. **自動樓梯/平地分類**：計算滑動窗口（最近 5 步）內 `|Δz| / sqrt(Δx²+Δy²)` 的比值：
   - 比值 < 0.08 → 判定「平地」（信心度依比值穩定度給 0–100%）
   - 0.08 ≤ 比值 < 0.9 → 判定「疑似樓梯/斜坡」，同時換算瞬時斜度 `θ = atan2(Δz, sqrt(Δx²+Δy²))`（單位：度），**這個角度完全由實測位移比值反推，不是程式硬編碼的假設值**
   - 比值 ≥ 0.9 → 判定「可能為電梯/手扶梯」（水平幾乎無位移但垂直持續變化，且無明顯步伐波形）→ 標記特殊片段，不套用一般步伐模型
4. 分類結果即時顯示在畫面上（例如路線圖該段變色＋標籤「樓梯 ↑ 約28°，信心度82%」），讓使用者走的時候就能大致確認系統有沒有抓到。
5. 原始感測器數據完整保留，主管或你事後可以重新畫出垂直加速度波形圖，人工核對程式判斷是否正確（因子#7根本對策——自動判斷有不可避免的誤判率，透明化比假裝100%準確更符合研究用途）。

### 4.4 零速度更新 ZUPT（因子#10對策，抑制積分發散的關鍵）

單純對加速度做兩次積分（線性→速度→位移）在手機 MEMS 等級感測器上，誤差會以時間三次方等級發散，走10幾秒就可能偏差好幾公尺，這是物理限制不是程式問題。本專案不做「連續積分」，改用步伐週期內的 ZUPT：

1. 每一步偵測到「腳著地瞬間」（垂直加速度波形由正轉負穿越零點後的局部極小值）視為該步的速度應趨近於 0 的時刻。
2. 在該時刻強制將垂直/水平速度估計值重置為 0，消除該步之前累積的積分誤差，避免誤差跨步傳遞。
3. 位移改用「步長模型（§4.2）× 航向角」直接給出每步的位移向量，而不是對加速度做長時間連續積分——這是業界 PDR 系統的標準做法，比純積分穩定得多。

### 4.5 迴圈閉合誤差（Loop Closure Error，給主管的精度參考指標）

- 若使用者在 UI 上勾選「這趟會走回起點」，停止時系統自動計算「推算終點」與「(0,0,0)」的直線距離，作為 `loop_closure_error_m` 一併輸出。
- 這個數字不是用來「修正」路線（本專案不做事後論文等級的閉環修正演算法，那是主管要比較的對象，不該由裝置端先做掉），而是單純作為這趟數據品質的參考指標，一併附在 metadata 裡。

```json
    "user_height_cm": 170,
    "start_time_iso": "2026-10-02T10:00:00.000Z",

  },
  "track": [
    { "t_ms": 0,     "x": 0.00, "y": 0.00, "z": 0.00, "segment_type": "flat", "confidence": 1.0 },
    { "t_ms": 620,   "x": 0.00, "y": 0.68, "z": 0.00, "segment_type": "flat", "confidence": 0.95 },
    { "t_ms": 5120,  "x": 0.12, "y": 3.40, "z": 1.85, "segment_type": "stairs_up", "slope_deg": 29.4, "confidence": 0.81 }
  ],
  "raw_sensor_log": [
    {
      "t_ms": 0,
      "acc": [0.12, -0.03, 9.79],
      "acc_linear": [0.01, 0.00, 0.02],

```

- `track[]`：事件驅動（每偵測到一步/一個轉折才新增一筆，不是定頻），欄位含該筆對應的分段類型與自動判斷信心度，方便主管篩選「只比較平地段」或「只比較樓梯段」。
- `raw_sensor_log[]`：定頻完整原始資料（頻率視裝置實際回傳，典型 30–60Hz），供事後重新套算法，是本專案對「公平比較」最重要的保底資料。
- CSV 版本拆成兩個檔：`track.csv`、`raw_sensor.csv`，欄位同上打平。

## 6. 使用流程與 UI 設計（簡單但不簡陋）

### 畫面一：設定頁
1. 使用者名稱/編號（必填，用於多人比較時標記身份）
2. 攜帶方式選擇（必填，4選項，見§4.2表）
3. 身高（選填，cm）
4. 「這趟會走回起點」開關（決定是否計算 loop closure error）
5. 權限請求按鈕：「允許使用動作與方向感測器」（iOS 13+ 需要 `DeviceMotionEvent.requestPermission()` 使用者手勢觸發；Android Chrome 通常不需要額外請求，但需 HTTPS）

### 畫面二：偵測中
- 上方：即時 3D 路線圖（Three.js），可手指拖動旋轉視角；下方附一個固定俯視 2D 投影圖（更好判斷「有沒有走歪」）
- 即時數據條：目前步數、目前推算距離、目前判斷（平地/樓梯上/樓梯下/電梯）+ 信心度百分比
- 大按鈕「停止」

### 畫面三：結果頁
- 完整路線 3D 圖（可旋轉、縮放，起點綠色、終點紅色標記，若閉環則顯示閉合誤差虛線）
- 摘要卡片：總步數、總時長、推算總距離、偵測到的樓層變化次數、閉合誤差（若有）
- 三個輸出按鈕：
  - 「複製 Track JSON」（純座標序列，給主管比較用）
  - 「下載完整數據包」（track + raw_sensor_log 一起的 JSON/CSV）
  - 「重新開始」

## 7. 已知限制與對主管的誠實揭露（重要，建議輸出檔也附上一份文字說明）

這段文字建議直接嵌入輸出 JSON 的 `metadata.disclaimer` 欄位，或獨立附一份 README 一起給主管，避免主管誤以為這是測量級定位：

1. 本數據為手機 MEMS 等級感測器的航位推算結果，非衛星/UWB/視覺定位等絕對定位技術，水平位移誤差會隨路徑長度與時間累積，一般室內走幾十公尺的誤差量級約在 5–15% 總距離，依手機型號、攜帶方式、使用者步態穩定性而異。
2. 樓梯斜度為自動反推值，非雷射測量值，僅供相對比較（例如比較「不同使用者反推出的斜度是否彼此接近、是否接近常見樓梯規範 30–35 度」），不建議當作精確建築測量數據使用。
3. 磁力計在電梯、金屬結構密集處會失準，系統有自動降權機制但無法完全消除該時段的航向誤差，對應時段信心度會在 `track[]` 中標示較低值。
4. 不同手機型號的感測器品質（取樣率、雜訊水準）差異頗大，跨裝置比較時，`metadata.device_info` 與 `avg_sample_rate_hz` 建議納入比較時的控制變因。

## 8. 開發階段建議（給後續實作參考）

1. **Phase 1（最小可行）**：感測器讀取＋權限流程＋原始數據記錄＋下載功能（先確保「忠實記錄」這條生命線做對，因為這是最終比較的真正依據）
2. **Phase 2**：姿態融合（Madgwick）＋步伐偵測＋水平2D PDR 路線（不含樓層）＋即時2D路線圖
3. **Phase 3**：垂直位移/樓梯自動判斷＋3D 可視化（Three.js）＋信心度標示
4. **Phase 4**：ZUPT 細化、動態步長個人化校正、磁場異常偵測降權、loop closure 計算
5. **Phase 5**：UI 打磨、CSV 匯出、多語系（如需要）、跨裝置相容性測試（iOS Safari / Android Chrome 行為差異較大，需各自測試權限流程）

## 9. 待確認事項（開發前建議再與主管確認一次）

- 多人比較時，是否要求所有人走「完全相同的實體路線」？若是，建議另外提供一份「標準路線圖」（紙本或照片）供所有測試者參照，這樣主管比較時才有一個共同的 ground truth 可以對照，否則「誰更精準」會缺乏客觀基準。
- 是否需要在網頁上提供「與已知路線疊圖比較」的功能，或者這部分完全交給主管在他自己的比較工具上做？（目前本規格書假設後者，網頁本身只負責產生乾淨可信的數據）
